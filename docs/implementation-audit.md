# AnquanDay 项目可行性与实施审计

审计日期：2026-11-09。本文是设计建议，不表示采集、生成、调度或网站已经实现。

后续更新（同日）：独立收集 engine 已实现，且已通过实际 HTTP/XML/JSON 与正文测试。本文保留首次审计时的观察；当前来源状态和执行结果请以 [逐来源实测报告](source-tests-2026-11-09.md) 与 [项目 README](../README.md) 为准。

## 1. 结论与项目定位

项目可行。建议定位为：**多来源的每日中文网络安全事件简报，按事件合并报道，每个关键事实保留可追溯的来源。**

首版体验建议：每天 5–12 条精选事件，每条约 80–150 个汉字，3–5 分钟读完；当天合格事件较少时允许少于 5 条。页面显示报道时间、事件发生时间（若已知）、可信度说明和原文链接。英文来源统一生成中文摘要，原文标题与链接保留。

“每日”建议表示当天新披露或有实质进展的信息；不能把今天发表的文章一律描述成今天发生的事故。

## 3. 来源核验的范围与限制

本次通过网页检索、官方页面和端点访问检查来源。另用本地 Python 对 14 个首页、RSS 或 API 地址尝试了匿名 GET；所有请求均在 DNS 解析阶段返回 `getaddrinfo failed`。这反映当前命令环境的联网限制，不能证明这些站点均已失效。

网页读取器对部分 RSS 返回 `Unsupported content-type: text/xml` 或 `application/rss+xml`。这说明读取器遇到 XML 类型响应，但**不等于已经解析并验证条目、日期和最新更新**。生产服务器的连通性、RSS 正确性、来源使用条件仍需逐项验收。

以下状态均是 2026-11-09 的一次性观察，不构成长期可用性承诺。

## 4. 首版产品范围

| 页面 | 首版行为 |
| --- | --- |
| 今日简报 | 重要事件在前；展示标题、短摘要、来源、状态、报道日期、更新时间 |
| 全部动态 | 浏览已收录事件，按日期、分类、来源、关键词筛选 |
| 历史日报 | 按日期读取当时发布的摘要快照 |
| 事件详情 | 关键事实、所有已获取报道、官方出处、后续进展与更正记录 |
| 来源状态 | 最近请求与成功时间、错误、抓到的条目数、最新条目日期 |

建议分类：重大攻击与勒索、数据泄露、漏洞与修复、APT/恶意软件、供应链与云安全、AI 安全、政策与执法。分类可以多标签，不强制每天每类都有内容。

单条事件卡片包含：中文标题；80–150 字摘要；受影响对象；发生/披露时间；证据状态；已验证的报道链接。证据状态使用“厂商已确认”“媒体报道”“攻击者声称，未独立证实”等可解释文字。

每日条数是阅读上限目标，不能为了凑数收录广告、招聘、课程促销、无实质进展的旧文或不相关犯罪新闻。

## 5. 采集与生成流程

1. **发现文章**：每个来源优先使用官方 RSS/API；缺失时使用有明确选择器的公开页面适配器。记录 ETag、Last-Modified、请求状态和来源独立的采集进度。
2. **获取与清洗**：规范化 URL、保存标题/时间/作者/来源，提取正文并去除广告、评论及导航。RSS 只有摘要时记录内容完整度；正文失败时只根据已读内容处理，不补写细节。
3. **文章去重与更新**：来源内 GUID、规范 URL 和内容哈希消除重复；同一 URL 正文变化作为修订。不要删除具有文章身份意义的查询参数。
4. **事件提取**：提取组织、产品、CVE、攻击类型、时间、事实和对应证据。早报或周报一篇可能包含多个事件，必须拆分；保留母文章出处，子链接只有在实际获取后才能作为已核验原文。
5. **跨来源归并**：通过实体、时间、CVE 和主题召回候选，再判断是否同一事件。相同 CVE 的不同受害事件不能直接合并；同一组织的不同事故也不能只按名称合并。保留人工拆分/合并入口。
6. **筛选与排序**：优先实际影响、在野利用、广泛受影响产品、紧急修复、可信新进展；可信度与重要性分开记录。转载自同一公告的五篇报道仍可能只有一个独立信息源。
7. **生成简报**：先对候选去重和筛选，再调用模型生成结构化中文结果。模型引用已提供的 article_id/evidence_id，由程序组装真实 URL；禁止模型创造引用链接。
8. **验证与发布**：校验字段、引用对应关系、关键数字/版本/CVE/日期、时间窗口和篇幅；失败项降级或进入待处理队列。使用数据库事务发布日报，保留旧版。

仅有链接不等于事实得到支持。关键主张应映射到证据片段，记录其来自正文还是 RSS 摘要。事实验证仍需要抽检，结构化输出本身不能保证正确。

来源之间若有冲突，保留归属与不确定性，例如分别注明“公司表示”和“攻击者声称”；不由模型自行选择一个数字作为定论。初期可人工检查排名前列及存在冲突的事件。

## 6. 时间、后续进展与日报一致性

- 分开记录 happened_at、published_at、updated_at、first_seen_at、fetched_at。未知发生时间允许为空，不用抓取时间填充。
- 内部统一存储 UTC，日报使用可配置的 IANA 时区。建议初始展示时区 Europe/Paris；如服务面向中国读者可改为 Asia/Shanghai。
- 产品默认建议：每 60 分钟抓取一次；每日当地时间 08:00 发布一期，覆盖前一发布截止点至本次截止点。此处仅为设计，尚未设置任务。
- 用半开区间和实际时区换算日期，正确处理夏令时，而非简单固定减去 24 小时。
- 按来源保存成功进度，重复回看近期条目以处理迟到和修订；失败后补抓，不能只取“现在往前 24 小时”并丢掉停机期间内容。
- 初次导入旧新闻只作历史基线；补抓旧文标记迟到收录，不称为当日事故。重要漏报可以明确标记后补。
- 同一事件出现新的受害规模、官方确认、补丁或调查结论时，标记“后续进展”并链接先前报道。没有新增事实时不重复进入次日日报。
- 日报保存摘要和引用快照；更新事件详情不能悄悄修改以前的日报。重新生成应产生版本并注明更正。

## 7. 建议技术架构与数据模型

建议使用 Python 3.12、FastAPI、Jinja2 和 MySQL，保持与 ArxivDay 接近的技术体系。一个 Web 进程负责页面/API，一个独立 worker 负责采集、归并与生成。数据库使用独立的 anquanday 库和受限账号。

可以把页面直接放到同一个 FastAPI 应用中，减少首版的服务间配置。ArxivDay 的页面组织、数据库连接和模型错误处理方式可参考，业务表、接口语义和摘要提示词需要按事件重新设计。依赖版本在实施时单独锁定并检查兼容性。

| 数据对象 | 建议字段或职责 |
| --- | --- |
| sources | 名称、类型、地址、启用状态、适配器、频率、ETag、健康状态、最后成功时间 |
| articles | 来源 ID、GUID、原始/最终/规范 URL、标题、各类时间、正文或许可范围内证据、内容哈希、提取状态 |
| events | 事件 ID、组织/产品/CVE、分类、首次披露/发生时间、当前摘要、证据状态、排序分量、最近重要进展 |
| event_articles | 多对多关系；标记报道、原始公告、转载依赖、关系判定依据 |
| event_claims | 关键事实、article_id、证据片段定位、内容哈希、是否存在争议 |
| digests | 日期、时区、起止截止点、版本、发布状态、生成配置版本 |
| digest_items | 顺序、事件 ID、标题/摘要/引用快照、是否后续进展 |
| job_runs | 任务键、来源/阶段、开始结束时间、重试、计数、错误、耗时和模型用量 |

文章与事件需要多对多关系，因为一篇早报包含多个事件，而一个事件也有多篇报道。小规模首版可以把实体、分类及证据定位存为结构化 JSON，后续再按检索需要拆表。

建议接口：GET /digests/latest、GET /digests/{date}、GET /events、GET /events/{id}、GET /sources/status、GET /healthz。生成、重试、更正等管理动作独立鉴权。

worker 使用持久化任务键与租约/锁，保证重复触发不会重复写入或重复发布。不要让每个 Web worker 都启动定时器。具体进程托管按最终部署主机选择；本次不改动运行环境。

## 8. 必须随首版处理的质量与运行问题

| 问题 | 首版设计 |
| --- | --- |
| 单站失败导致整期失败 | 逐来源隔离、有限重试、退避和超时；日报显示覆盖不足 |
| RSS 返回 200 却是验证页或旧缓存 | 校验类型、XML 结构、条目、日期；同时记录请求成功与内容新鲜度 |
| 低频媒体被误报故障 | 按来源正常更新节奏设阈值；“没有新文章”与“请求失败”分开 |
| 超时/429 | 尊重 Retry-After；限并发，限制抓取体积，复用条件请求 |
| 页面结构变化 | 低正文长度、标题异常或选择器失效时停止自动发布该来源内容 |
| 模型失败 | 重试后保留可用标题、来源和原始摘要，明确处理状态；不生成无证据摘要 |
| 模型费用膨胀 | 先规则过滤、去重；只处理新增或重要修订；按内容哈希、模型和提示词版本缓存，设置日预算 |
| 提示注入 | 网页只作为数据；摘要模型不获得命令执行、任意浏览或发布工具；输出经固定 schema 和引用校验 |
| SSRF 和恶意重定向 | 来源白名单、HTTP(S) 限制；请求及每次跳转校验目的地址，阻止回环/私网/元数据地址；限制跳转次数 |
| HTML/Markdown 注入 | 正文与输出统一净化/转义，拒绝脚本及危险链接协议 |
| XML 与资源耗尽 | 禁止外部实体解析，限制解压后体积、条目数、处理时间与嵌套资源 |
| 密钥和管理操作 | 密钥放环境变量，不进入前端或日志；管理动作鉴权，Cookie 管理会话需 CSRF 防护 |
| 来源内容使用 | 展示独立短摘要、署名与链接；逐来源核查抓取和使用条件，原文缓存策略可配置，不默认公开复制全文 |

以上是与本系统输入和发布链路直接相关的设计要求，不代表已发现 ArxivDay 存在对应漏洞。

## 9. 开发顺序与验收

### 阶段 A：来源验证和采集样本

在拟部署主机上逐一验证候选 RSS/API 的 HTTP 状态、最终地址、媒体类型、条目解析、最近发布时间、正文覆盖、分页及使用条件；再测试暗网下公开页面适配器。至少接入 3 个能稳定工作的新闻来源，并独立验证官方通告或 KEV 来源。

记录连续多个采集周期的结果，区分工作日、周末及低频媒体。至少连续运行 72 小时用于工程观察，但不据此承诺长期可靠。

### 阶段 B：事件与简报处理

使用真实采集样本人工核查至少 30 个候选事件，覆盖中英转载、同一 CVE 的不同事故、无 CVE 的泄露、早报拆分、旧闻补抓及后续更正。确认引用支持摘要、归并合理后，再生成固定版本日报。

### 阶段 C：页面与无人值守运行

实现今日简报、事件详情、历史日报和来源状态，加入单 worker 调度、持久化、备份、预算及可观察日志。确认断网、来源失败和模型失败时仍能读取历史内容。

验收清单：

1. 每条已发布事件至少有一个真实获取、可识别出处的来源；引用链接由存储记录产生。
2. 摘要关键事实可定位到证据；标题、数字、CVE、版本和确定性表述没有人工抽检发现的实质偏差。
3. 重跑同一批次不会重复写入文章、事件或日报。
4. 一篇多事件早报能拆分，一个事件的多篇报道能合并；相似但不同事故不会误合并。
5. 单一来源失败不阻断其他来源；覆盖不足有可见提示，不误报“今天没有安全事件”。
6. 初始导入、迟到文章、跨日修订和夏令时边界都有明确结果。
7. 历史日报快照保持一致；更正可追踪。
8. 模型超时、无效 JSON、虚构 article_id、正文缺失等输入不会绕过发布校验。
9. 页面内容净化、抓取目标限制和管理操作鉴权验证通过。

这些测试覆盖真实故障和业务边界；普通文案或样式调整无需额外镜像测试。

## 10. 成本与上线前尚待验证项

成本主要来自正文提取、模型摘要与持续来源维护。例：8 个来源每小时轮询一次约 192 次 feed 请求/日，正文只对新增或修订文章按需抓取；这只是请求量示例，不是实际已观察负载。

模型成本用实际输入/输出 token、模型价格、失败重试及缓存命中率计算。此时尚未选择模型或运行样本，不给固定月费承诺。

仍待验证：部署位置与外网出口；候选端点的实际解析与更新；各站抓取和摘要展示条件；实际每日文章量；中文来源覆盖；跨语言合并与摘要质量；目标数据库和服务托管配置。上述事项不影响先完成来源适配和样本验证。
